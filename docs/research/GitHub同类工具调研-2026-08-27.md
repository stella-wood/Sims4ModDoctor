# Sims 4 Mod Sieve｜GitHub 同类工具与可复用组件调研

> 调研日期：2026-08-27  
> 对齐基线：PRD `0.15-review`、架构方案 v3  
> 目的：确认是否已有可直接采用的产品或底层组件，减少重复造轮子，同时不牺牲本项目已经确认的安全边界和产品结构。

---

## 1. 结论先行

GitHub 上已经存在若干相似工具，但**没有找到一个可以直接作为 Sims 4 Mod Sieve 成品底座的成熟项目**。

主要原因不是功能名称不同，而是现有项目通常至少缺少以下一项：

- 重复检测与冲突检测的独立入口、配置和报告；
- 任意多目录以及父目录／子目录同时选择的范围语义；
- 健康检查、内部冲突、最近报错诊断三条独立证据链；
- 四级行动优先级与独立可信度；
- Windows 回收站、逐文件结果和最近一次轻量撤回；
- 足够的真实样本、自动测试和损坏输入防御；
- 允许合法复用代码的明确许可证。

不过，确实找到了三类可以少造的轮子：

1. **首选复用：DBPF 读取与解压能力。** 推荐先验证 MIT 许可的 `LlamaLogic.Packages`；如果采用 .NET 8，它可以直接作为依赖。
2. **可借鉴设计：冲突关系图和结果分组。** `sims-mod-assistant` 已证明“文件—资源键—冲突组”的图模型可行，但代码停留在 2020 年，只能参考或局部移植。
3. **可借鉴平台操作：回收站逐文件处理。** `sims-file-manager` 的 Electron `shell.trashItem` 与逐文件成功／失败回报符合我们的安全方向；若不采用 Electron，则只借鉴行为契约。

因此，推荐策略不是 fork 某个同类产品，而是：

```text
保留自己的产品层、范围模型、报告模型和安全动作
                  │
                  ├─ 复用成熟 DBPF 库
                  ├─ 借鉴已有冲突图算法
                  └─ 使用所选桌面栈的系统回收站接口
```

## 2. 调研方法与证据边界

本次通过 GitHub 搜索找到候选仓库，并对重点候选进行了只读浅克隆和静态代码检查，检查内容包括：

- 最近提交时间、仓库规模和目录结构；
- 是否有明确的根许可证；
- README 声称的能力是否能在实现中找到；
- DBPF header、index、constant fields、压缩处理方式；
- 哈希、重复分组、冲突分组与删除／移动行为；
- 自动测试和真实 package fixture。

没有运行来源不明的安装器、批处理或候选工具，也没有拿 Stella 的真实 Mods 集合作测试。

星数、README 和提交数量只用于判断维护信号，不代替代码审查和真实样本验证。

## 3. 最接近本产品的项目

### 3.1 Sims 4 Mod Assistant

- 仓库：[EgorBlagov/sims-mod-assistant](https://github.com/EgorBlagov/sims-mod-assistant)
- 许可证：ISC，可复用但必须保留许可证声明。
- 技术栈：Electron 9、TypeScript 3.9、React。
- 最后提交：2020-09-20。
- 与本项目重合：精确重复、DBPF TGI 冲突、冲突分组、批量选择、移出目录、Sims 4 Studio 联动。

值得借鉴：

- 它把每个文件映射为一组冲突键，再将共享键的文件聚合成连通关系，方向与 v3 的“多重集合＋倒排＋关系图”一致。
- 它没有把所有 TGI 重叠都混成一个平面列表，而是保留冲突组及共享键摘要。
- 对 Catalog、Definition、Skintone、CAS Part、HotSpot 等类型分别筛选，说明“按资源类型解释覆盖”比无差别报警更适合玩家。

不能直接采用：

- 技术栈和依赖已经明显老化；只接受 DBPF `2.1`，边界较窄。
- 精确重复使用 MD5，并一次性读取完整文件；不满足我们对大库流式 SHA-256、稳定性复核和性能证据的要求。
- 自动测试只有少量路径关系测试，没有覆盖 DBPF parser、重复分组或冲突图。
- 文件动作是移动到另一个目录，不是 Windows 回收站，也没有最近一次撤回语义。
- 没有健康检查、日志诊断和我们定义的独立报告边界。

定位：**算法与交互参考，不作为现成底座。**

### 3.2 Sims File Manager

- 仓库：[andylpzm/sims-file-manager](https://github.com/andylpzm/sims-file-manager)
- 许可证：MIT。
- 技术栈：Electron 43、Next 16、React 19、Node 20+。
- 最后提交：2026-08-03。
- 与本项目重合：大小分组、局部哈希、流式 SHA-256、精确重复、批量清理、系统回收站、部分失败回报。

值得借鉴：

- Electron 主进程使用 `shell.trashItem`，批量操作逐文件执行并分别返回成功和失败，符合“部分失败不能污染整批结果”。
- 跳过符号链接、限制并发 `stat`、迭代式遍历和节流进度事件，都是实用的桌面扫描经验。
- 删除界面明确保护要保留的副本，和本项目“不允许误删全部副本”的方向一致。

不能直接采用：

- 只有单目录扫描，不支持多入口、父子范围图和两套独立配置。
- 先读 4 KiB 再对候选读完整文件，同一候选会被读取两次；我们的实现需要明确是否接受这个性能折中。
- “同名但内容不同即不同版本”只是文件名启发式，不能升级为已确认的版本冲突。
- 没有 DBPF 资源分析、健康检查或日志诊断，也没有自动测试。

定位：**回收站行为和扫描工程经验参考；不能替代产品核心。**

### 3.3 近期的两个高相似 Python 项目

候选：

- [Matthew-Oj/sims-4-mod-manager](https://github.com/Matthew-Oj/sims-4-mod-manager)
- [Mecapixel/sims4-mod-detector](https://github.com/Mecapixel/sims4-mod-detector)

两者 README 都声称支持精确重复、DBPF/TGI 冲突和损坏 Mod 检测，第二个还声称支持 MCCC／Better Exceptions、版本检查和合并包分析。

静态检查后不建议复用：

- 两个仓库根目录都没有 LICENSE。没有许可证不等于可以自由复制；默认只能把公开行为当作需求线索，不能拿代码进入本项目。
- 仓库都很小，分别约 12 和 14 个文件，缺少覆盖核心解析器的自动测试。
- 前者按固定 24 字节读取资源键，没有处理 DBPF constant fields，最多读取前 100 个键，不能作为冲突分析底座。
- 后者虽然读取 constant fields，但通过“剩余索引长度／条目数”猜每条记录的布局，解压失败时可能返回原始压缩数据；这会制造难以识别的假结论。
- 后者还在代码中维护静态“坏 Mod／安全版本”名单；没有可信更新链时，这类知识会快速过期，不应混入离线事实层。

定位：**需求雷达和反例；不复制代码、不作为依赖。**

## 4. 可以真正复用的 DBPF 底座

### 4.1 首选候选：LlamaLogic.Packages

- 仓库：[Llama-Logic/LlamaLogic](https://github.com/Llama-Logic/LlamaLogic)
- 组件：`LlamaLogic.Packages` NuGet 包。
- 许可证：MIT。
- 当前检查版本：3.8.2，目标框架覆盖 .NET 6–9。
- 最近提交：2026-08-25。

静态检查确认它提供：

- 由路径或流打开 DBPF；
- 列出 `ResourceKey`、数量和尺寸；
- 获取原始或解压后的资源；
- Internal／RefPack 与 zlib 压缩处理；
- XML、STBL、ModFileManifest 等上层模型；
- 同步和异步 API；
- TS2、TS3 和 TS4 package fixture 以及 package 单元测试。

对本项目最重要的是：冲突检测只需读取 `Keys`／`GetKeys` 就能建立 TGI 倒排，只有碰撞资源才调用 `GetRaw` 或 `Get`。这正好保留 v3 的“先索引、后按需解压”数据流，不需要自己重写 DBPF 格式细节。

代价与风险：

- 直接依赖它意味着核心后端优先采用 .NET；如果 UI 继续选择 Python 或 Web 栈，就需要进程间接口，反而增加复杂度。
- 库的能力超过本项目首版所需，必须包在自己的只读 `PackageReaderPort` 后，不让写 package 的 API 泄漏进应用层。
- 仍需用 Stella 的真实 package 语料与 s4pe 对拍；第三方库不能替代我们的验收门。

定位：**当前最值得复用、也最可能改变技术栈选择的组件。**

### 4.2 TypeScript 备选：Sims 4 Toolkit Models

- 仓库：[sims4toolkit/models](https://github.com/sims4toolkit/models)
- npm 包：`@s4tk/models`
- 许可证：MIT。
- 仓库有较长历史和测试，但 README 明确标为 pre-release，可能发生破坏性变化。

如果决定使用 Electron／Tauri Web UI，这是一条比移植旧 `sims-mod-assistant` parser 更合理的路线。需要在 spike 中验证：

- 只读打开大型 package 的内存行为；
- constant fields 与压缩类型覆盖；
- API 的版本稳定性和锁版本策略；
- Windows 打包后的扫描吞吐。

定位：**Web 桌面栈的正式备选。**

### 4.3 Python 备选：sims4-workspace 的 package reader

- 仓库：[gbataglini/sims4-workspace](https://github.com/gbataglini/sims4-workspace)
- 许可证：MIT。
- 最近提交：2026-05-15。

它包含清晰的 Python `PackageReader`、constant fields、zlib、RefPack/QFS 和资源类型表，也有较多 RefPack 测试。

但当前 DBPF parser 测试使用自造的 `flags=0` package，仓库内没有真实 `.package` fixture，也没有覆盖 constant fields 全组合。它更接近“可以抽取并继续加固的实现”，还不能作为未经验证的稳定依赖。

如果坚持 Python，应当：

1. 保留 MIT 声明并明确记录抽取来源；
2. 将 parser 独立为受限只读模块；
3. 补 constant fields 全组合、截断、越界和恶意 count；
4. 用同一批真实 package 与 LlamaLogic／s4pe 三方对拍；
5. 在通过前只返回“未完成分析”，不得输出健康结论。

定位：**Python 路线的可加固起点，不是开箱即用依赖。**

### 4.4 验证 oracle：s4pe / Sims4Tools

- 仓库：[s4ptacle/Sims4Tools](https://github.com/s4ptacle/Sims4Tools)
- 许可证：GPL-3.0。
- 定位：成熟的 package 查看／编辑工具和验证参照。

它仍适合作为真实样本对拍工具，但不建议直接链接或复制到一个许可证尚未决定的产品中。若复用 GPL 代码，需要单独决定整个产品的许可证兼容策略。

## 5. Build / Buy / Borrow 决策

| 能力 | 决策 | 理由 |
|---|---|---|
| 产品入口、配置与报告边界 | Build | PRD 的双入口和独立结果是本项目核心，没有现成工具完整匹配 |
| 多目录与父子范围图 | Build | 现有项目普遍只选一个根目录 |
| 精确重复分组 | Build 小核心 | 算法简单，但“保留哪份”和范围语义是产品规则 |
| SHA-256 流式读取 | 使用标准库 | 不需要引入 Sims 专用依赖 |
| DBPF header/index/解压 | Buy/Borrow | 首选 `LlamaLogic.Packages`，避免重写格式细节 |
| TGI 倒排和冲突关系 | Build + 借鉴 | 算法需服从我们的事实／影响／可信度模型，可参考旧工具图结构 |
| 健康检查 | Build 检查器框架 | 只接入有证据和版本边界的规则 |
| MCCC／游戏日志解析 | Build 独立适配器 | 格式可变，必须可降级并标记未完成 |
| Windows 回收站 | 平台 API／成熟封装 | 不自建隔离区，不用永久删除模拟回收站 |
| s4pe | Verify | 用作 oracle，不默认嵌入产品 |

## 6. 推荐技术决策

### 推荐方向

在开始正式编码前，将原先隐含的 Python 选择暂停，先做一个很小的技术 spike：

```text
.NET 8 console spike
├─ LlamaLogic.Packages 读取真实 package
├─ 输出所有 ResourceKey 与压缩元数据
├─ 与 s4pe 对拍
├─ 测大型 Mods 目录吞吐与内存
└─ 验证 Windows 回收站接口
```

若 spike 通过，推荐首版采用：

- **后端与桌面主进程：.NET 8**；
- **DBPF：LlamaLogic.Packages，包在本项目只读适配器后**；
- **UI：WPF、WinUI 3 或 Avalonia 三选一，另做最小界面 spike 决定**；
- **存储：SQLite**；
- **回收站：Windows Shell API 或经真实测试的 .NET 封装**。

选择 .NET 不是因为 Python 做不到，而是本项目首发只支持 Windows，且最可信、活跃、宽松许可的 DBPF 轮子已经在 .NET 生态里。为了保留 Python 而跨进程调用 .NET，会把省下的解析器工作重新花在部署和 IPC 上。

### 退路

如果 .NET UI 或打包体验不合适，再比较：

1. Electron／TypeScript + `@s4tk/models`；
2. Python + 抽取并加固 `sims4-workspace` parser。

不建议以两个无许可证的近期 Python 项目为起点，也不建议从零重写完整 DBPF parser 后才开始真实样本验证。

## 7. 对 v3 的直接影响

架构方案 v3 应同步做以下变化：

- 将项目结构视为逻辑模块，不再用 `.py` 文件名提前锁定 Python；
- 在阶段 A 前增加“技术栈与 DBPF 依赖 spike”准入门；
- 阶段 C 从“实现 DBPF 解析器”改成“验证并封装 DBPF 读取能力”；
- 第三方 parser 必须位于只读适配器后，并保留许可证清单；
- s4pe 继续作为独立 oracle，不自动成为运行时依赖；
- 任何来自无许可证仓库的代码都不得复制进入项目。

本调研结论不改变 PRD 的产品边界，只改变底层实现的 build／borrow 比例。
