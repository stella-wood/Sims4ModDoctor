# Sims 4 Mod Doctor 架构方案 v3

> 状态：与 PRD `0.15-review` 对齐的讨论稿  
> 目标平台：Windows，本地离线运行  
> 产品权威来源：[`产品需求文档`](../product/产品需求文档.md)  
> 开源复用决策：[`GitHub 同类工具调研`](../research/GitHub同类工具调研-2026-08-27.md)  
> 本文职责：说明如何实现已经确认的产品结构、能力边界、数据流、模块边界和分期验证方式；本文不反向改写产品需求。

---

## 1. 本版对齐结论

Sims 4 Mod Doctor 是一个统一的本地桌面产品，但包含两个可以独立进入、独立配置、独立运行并独立保存结果的核心功能：

1. **重复文件检测**：回答“哪些本地文件内容完全相同，哪些副本可以由用户考虑删除”。
2. **Mod 冲突检测**：回答“所选 Mod 是否损坏、是否存在资源重叠、最近错误日志提供了哪些线索”。

产品可以额外提供“一键体检”，但它只是一个组合调度器：

```text
一键体检
├─ 调用一次独立的重复文件检测
└─ 调用一次独立的 Mod 冲突检测
```

组合运行不会产生第三种检测算法，也不会合并、覆盖两项功能各自的配置和报告。

### 1.1 v2 中被本版替换的设计

| v2 设计 | v3 对齐结果 |
|---|---|
| 首页使用“快速体检／完整体检” | 首页使用“重复文件检测／Mod 冲突检测”；一键体检为可选第三入口 |
| 主要围绕一次 Mods 目录选择组织 | 重复检测支持任意多目录；冲突检测保存独立的 Mods 内局部范围 |
| 最终输出一份统一报告 | 两类报告独立保存；组合运行只建立关联并分标签展示 |
| 后续使用自有隔离区 | 不建立隔离区；删除进入 Windows 回收站，并最多支持最近一次批量删除的轻量撤回 |
| 冲突检测主要等于 TGI 重叠 | 冲突检测内部拆为健康与兼容性、多项内部冲突、最近报错诊断 |

v2 中的文件指纹、DBPF/TGI、防御性解析、碰撞后再解压、事实与推测分离等底层原则继续保留。

## 2. 架构原则

### 2.1 用户任务决定前端边界

- 前端页面、运行状态和报告入口按玩家任务划分，不按 hash、DBPF、日志解析器等技术模块划分。
- 技术模块可以复用，但不能让内部依赖变成用户必须先完成的操作。
- 默认只展示玩家可以采取行动的结论；SHA-256、TGI、资源编号、调用栈等证据按需展开。
- 系统能够静默应用可靠默认行为时，不向用户展示“我推断了你的意图”之类的过程说明。

### 2.2 默认只读，写操作单独授权

- 扫描、解析、缓存和报告生成不得修改 Mod 文件。
- 文件删除只能来自用户明确勾选的实际文件。
- 自动规则只能生成勾选状态，不得直接执行删除。
- 第一阶段不编辑 package 内部资源，不自动修复、更新、合并或替换 Mod。

### 2.3 事实、影响与可信度分离

至少区分：

```text
事实：是否重复、是否损坏、是否存在相同 TGI、内容是否相同
影响：玩家是否需要处理，以及处理优先级
可信度：已确认、高度疑似、可能相关、信息不足
```

“已确认存在覆盖”不等于“已确认有害”。同一条发现必须能够同时表达事实、行动优先级和判断可信度。

### 2.4 局部失败不能污染整体结果

- 单个文件损坏、权限不足或格式不受支持时，继续处理其余文件。
- “未发现问题”和“未完成分析”分开统计。
- 组合体检中一项失败时，另一项的有效结果仍然保存。
- 取消运行只取消对应任务，不删除另一功能的历史结果。

### 2.5 证据边界

- 第一阶段只正式支持 Windows 上的《模拟人生 4》PC 版。
- 当前只有一名真实测试者；本机成功不能自动升级为多用户或跨平台支持。
- macOS、Linux、Wine、Proton、NAS 和其他远程文件系统均不进入首轮正式支持。
- 不承诺离线静态分析能够发现所有游戏崩溃或运行时逻辑错误。

### 2.6 第三方组件边界

- 优先复用经过维护、许可明确且可用真实样本验证的格式库，不以“代码量少”为由重写完整 DBPF 生态。
- 第三方 package 库必须位于本项目只读适配器之后；第一阶段不得向应用层暴露写入、合并或修改 package 的能力。
- 无明确许可证的公开仓库只能作为需求与反例参考，不得复制代码。
- GPL 组件默认仅作为独立验证工具；是否成为运行时依赖必须另行完成许可证决策。
- 第三方库成功解析不等于产品分析完成，仍需执行资源上限、结构化错误、真实语料和 oracle 对拍。

## 3. 系统边界与分层

```text
┌────────────────────────────────────────────────────┐
│                    Desktop UI                       │
│  首页 / 重复检测 / 冲突检测 / 一键体检 / 历史结果  │
└───────────────────────┬────────────────────────────┘
                        │ application commands
┌───────────────────────▼────────────────────────────┐
│                 Application Layer                  │
│ DuplicateRunService / ConflictRunService           │
│ CheckupCoordinator / ResultQueryService            │
│ FileActionService                                   │
└───────────────┬───────────────────┬────────────────┘
                │                   │
┌───────────────▼──────────┐ ┌──────▼────────────────┐
│       Domain/Core        │ │      Infrastructure    │
│ 扫描范围、发现、等级、    │ │ 文件系统、DBPF、日志、 │
│ 可信度、关系与报告模型    │ │ SQLite、回收站、报告    │
└──────────────────────────┘ └───────────────────────┘
```

### 3.1 UI 层

UI 只负责：

- 收集玩家选择；
- 展示本次范围、模式、进度与结果；
- 将用户动作转换为应用层命令；
- 展示玩家语言摘要并按需展开技术证据。

UI 不直接遍历磁盘、不直接解析 DBPF、不直接判断风险，也不自行删除文件。

### 3.2 应用层

应用层负责一次用例的完整编排：

- 创建运行快照；
- 调用扫描与分析模块；
- 汇总进度、取消和错误；
- 保存独立报告与历史状态；
- 在一键体检中关联两次独立运行。

### 3.3 核心与基础设施层

核心层保存稳定的领域模型和纯判断逻辑；基础设施层处理文件系统、格式解析、缓存、报告序列化和 Windows 回收站等平台行为。

## 4. 配置与运行状态隔离

### 4.1 全局设置

两项功能仅共享真正属于产品级或游戏位置的设置：

```text
GlobalSettings
├─ locale
├─ theme
├─ performance_options
├─ sims4_user_root
└─ confirmed_mods_root
```

`confirmed_mods_root` 是经过确认的游戏位置，不代表两项功能共享完整扫描范围。

### 4.2 重复检测配置

```text
DuplicateConfig
├─ scan_sources[]
│  ├─ path
│  ├─ enabled
│  ├─ explicit_order
│  └─ source_label
├─ include_extensions[]
└─ last_run_id
```

重复检测可以没有 Mods 目录，也可以包含多个外部目录。暂时取消勾选不删除来源记录。

### 4.3 冲突检测配置

```text
ConflictConfig
├─ mods_root
├─ mode                 # health / internal_conflict / recent_error
├─ selected_scopes[]    # Mods 内文件或目录
├─ scan_options
├─ log_sources
└─ last_run_id_by_mode
```

重复检测中的外部目录不得自动进入冲突检测；冲突检测的局部选择也不得覆盖重复检测配置。

### 4.4 运行快照

每次运行开始时，将当时的配置复制为不可变快照：

```text
RunSnapshot
├─ run_id
├─ feature
├─ mode
├─ selected_scope_snapshot
├─ started_at
├─ completed_at
├─ status
├─ app_version
└─ capability_version
```

报告引用运行快照，而不是读取可能已被用户修改的当前配置。

## 5. 共用文件发现管线

重复检测和冲突检测可以复用文件发现、稳定性检查和错误收集，但必须由各自的运行服务提供范围。

```text
输入范围
  │
  ▼
路径规范化与可访问性校验
  │
  ▼
建立显式范围关系
  │
  ▼
安全递归遍历
  │
  ├─ 不跟随 reparse point
  ├─ Unicode / 长路径
  └─ 单文件错误不中断
  │
  ▼
生成 FileSnapshot
```

### 5.1 FileSnapshot

```text
FileSnapshot
├─ normalized_path
├─ display_path
├─ size
├─ mtime_ns
├─ extension
├─ selected_scope_ids[]
├─ physical_identity?      # 能可靠获得时使用
└─ discovery_error?
```

扫描前后比较文件大小与修改时间。文件发生变化时稍后重试一次；仍不稳定则记入“未完成分析”，不得输出旧 hash。

### 5.2 重叠目录的读取去重与语义保留

当显式选择存在父子关系时：

1. 建立显式选择的包含关系树；
2. 每个实际文件只进入读取管线一次；
3. 文件保留自己命中的全部显式范围标识；
4. 显式子目录作为重点范围；
5. 父目录的比较域为排除所有显式子范围后的剩余内容；
6. 结果分区时优先归入“重点范围 ↔ 参照范围”，同一重复组只出现一次。

实现可以使用规范化路径与 Windows 文件标识辅助去重，但不得跟随 junction 或符号链接扩大范围。

## 6. 重复文件检测架构

### 6.1 数据流

```text
DuplicateRunService
  │
  ├─ FileDiscovery
  ├─ 按 size 分组
  ├─ 仅对同大小候选计算流式 SHA-256
  ├─ 生成 DuplicateGroup
  ├─ 根据显式范围关系分区和排序
  └─ 保存 DuplicateReport
```

### 6.2 重复判定

1. 按文件大小分组；
2. 大小唯一的文件跳过 SHA-256；
3. 对同大小组分块读取并计算 SHA-256；
4. hash 相同的文件进入同一重复组；
5. 文件名、修改时间、目录和扩展名不参与“内容完全相同”的最终判断。

为防止扫描过程中替换文件导致错误结果，hash 前后必须再次验证文件稳定性。

### 6.3 结果分区

```text
DuplicateReport
├─ summary
├─ focus_cross_scope_groups[]
├─ focus_internal_groups[]
├─ reference_internal_groups[]
├─ ordinary_groups[]
└─ incomplete_files[]
```

没有显式父子关系时只使用普通重复组。存在多个重点子范围时，使用稳定的显式选择顺序与范围标识生成不重复分区。

### 6.4 一键勾选重复副本

该能力属于结果层的纯选择算法，不执行文件操作。

每组保留恰好一份，候选排序为：

```text
1. 当前 Mods 内部优先于外部目录
2. 真实目录层级更深者优先
3. 规范化路径按稳定字典序决胜
```

第三条只是让 PRD 中“任意稳定保留一份”可重复验证；UI 不需要向普通玩家解释该技术决胜规则。

限制：

- 只对整个文件 SHA-256 完全一致的组生效；
- 不应用于相同 TGI 但 payload 不同的资源覆盖；
- 自动选择后允许用户任意取消或补充；
- 用户必须再执行一次明确的“删除所选”。

## 7. Mod 冲突检测架构

冲突检测不是单一算法，而是共享范围与证据模型的三个独立用例。

### 7.1 健康与兼容性检查

目标：对整个 Mods、单个文件或局部目录执行游戏前静态检查。

第一阶段可逐步接入以下检查器：

```text
HealthCheckPipeline
├─ PackageStructureCheck
├─ DbpfIndexBoundsCheck
├─ ScriptArchiveStructureCheck
├─ ScriptModuleCollisionCheck
├─ DependencyEvidenceCheck
├─ GameRequirementEvidenceCheck
├─ ResourceReferenceCheck
├─ FormatCompatibilityCheck
└─ VanillaOverrideInfoCheck
```

不是所有检查器都必须在首版启用。报告必须保存本次实际启用的 capability 清单；未运行的检查不得表现为“已通过”。

原版资源覆盖需要一个可验证的游戏资源索引来源。架构预留：

```text
GameResourceIndexProvider
├─ LocalGameIndexProvider
└─ VersionMatchedPrebuiltIndexProvider
```

首版采用哪一种仍按 PRD 待定事项处理。在来源未实现或版本不匹配时，只能标记该能力未完成，不能猜测。

### 7.2 多项内部冲突

用户选择多个文件或目录后，只展开这些范围：

```text
Selected scopes
  │
  ├─ 共用文件发现
  ├─ 本次范围内完全重复检测
  ├─ 解析 .package DBPF 索引
  ├─ 建立 TGI 倒排表
  ├─ 只读取碰撞资源 payload
  └─ 生成重叠、覆盖、包含与未知结果
```

未选择的其他 Mods 不得偷偷加入比较范围。附带重复结果单独保存到报告分区，不与资源覆盖混为同一种问题。

### 7.3 最近报错诊断

优先读取：

- Sims 4 原生 `lastException`；
- Sims 4 原生 `lastUIException`；
- 可选的 MCCC `mc_lastexception.html`。

```text
LogDiagnosticPipeline
├─ LogSourceDiscovery
├─ ParserBySourceType
├─ NormalizedStackEvidence
├─ ModPathOrModuleCorrelation
├─ RepetitionAndRecencySummary
└─ DiagnosticFinding[]
```

约束：

- MCCC 只是增强来源，未安装时功能仍可使用；
- 修改时间只用于组织日志，不能单独证明唯一责任 Mod；
- 调用栈、模块名、重复出现次数和已知映射均作为证据保存；
- 无法可靠映射到具体 Mod 时，报告必须保留“信息不足”。

## 8. DBPF 与资源关系分析

### 8.1 已知基础

- magic：`DBPF`；
- Sims 4 常见文件版本：major `2`、minor `1`；
- header：96 字节；
- 小端序；
- TGI：Type `uint32`、Group `uint32`、Instance `uint64`。

版本和压缩支持必须以真实样本验证为准；未知版本不得强行按已知布局解析。

### 8.2 indexType constant fields

索引开头的 `indexType` flags：

- `0x01`：Type 为公共常量；
- `0x02`：Group 为公共常量；
- `0x04`：Instance 高 32 位为公共常量。

解析器必须按 flags 动态读取公共字段和记录字段，禁止假设每条记录固定长度。

### 8.3 防御性校验

在任何 seek、解压或内存分配前验证：

- 文件长度不小于 header；
- magic 与版本受支持；
- index position、size、count 在合理范围；
- 每条记录剩余字节充足；
- resource offset 与 stored size 不越界；
- 32／64 位整数运算不溢出；
- 解压后大小不超过配置的安全上限；
- 损坏索引不能触发按伪造 count 进行巨大分配。

解析失败只影响当前文件，并生成结构化错误原因。

### 8.4 TGI 倒排与按需 payload

为每个非删除资源保存：

```text
ResourceEntry
├─ package_path
├─ ordinal
├─ type
├─ group
├─ instance
├─ offset
├─ stored_size
├─ memory_size
├─ compression
└─ payload_sha256?
```

倒排表：

```text
(type, group, instance) -> [ResourceEntry, ...]
```

只有列表长度大于 1 的 TGI 才进入 payload 比较：

1. 存储字节完全一致时，可直接判定当前存储内容相同；
2. 否则按受支持方式解压；
3. 对解压 payload 计算 SHA-256；
4. payload hash 相同：资源内容相同；
5. payload hash 不同：已确认存在内容覆盖；
6. 无法解压：已确认重叠，内容关系未知。

### 8.5 package 关系

支持表达：

- 文件完全相同；
- 资源等价；
- A 被 B 完整包含，且内容相同；
- A 的资源键被 B 包含，但部分内容被修改；
- 部分重叠；
- 疑似版本关系。

文件名和目录只能作为疑似版本关系的辅助信号。相似度阈值必须通过真实 Mod 样本调试，不能先写成通用事实。

### 8.6 加载顺序

首版不宣称能够确定最终生效 package。只有完成以下控制实验后，才允许增加“预计生效文件”：

- 交换同 TGI 测试包文件名；
- 交换目录层级；
- 修改 `Resource.cfg` Priority/PackedFile；
- 固定并记录游戏版本；
- 重复观察游戏内明显差异。

推断功能必须显示依据，并允许当前环境无法确定。

## 9. `.ts4script` 分析边界

`.ts4script` 与 DBPF package 使用不同分析器。

分期能力：

1. 作为普通文件参与 SHA-256 完全重复检测；
2. 校验 ZIP 中央目录与条目可读性；
3. 提取 Python 模块路径清单；
4. 检测同名模块碰撞；
5. 结合内容与辅助版本信息生成疑似新旧脚本候选。

脚本模块碰撞不得混入 TGI 模型。即使模块同名，也要区分内容相同、内容不同和无法读取。

## 10. 发现、等级与报告模型

### 10.1 统一 Finding 模型

```text
Finding
├─ finding_id
├─ feature
├─ check_type
├─ relation_type
├─ affected_files[]
├─ action_level           # 1..4
├─ confidence             # confirmed / highly_suspected / possible / insufficient
├─ player_summary
├─ suggested_action?
├─ evidence[]
├─ capability_id
└─ status                 # active / accepted / file_removed / stale
```

### 10.2 四级处理优先级

- 等级 1：必须处理；
- 等级 2：建议优先处理；
- 等级 3：可能影响部分功能；
- 等级 4：信息提示。

默认问题列表只展示等级 1 至 3。等级 4 只进入聚合统计、单项详情或高级信息。

### 10.3 报告摘要

```text
已发现文件
已完成分析
未发现需处理问题
需要查看
未完成分析
```

“未完成分析”保存能力名称和原因，不能计入健康。

### 10.4 独立报告

```text
DuplicateReport
```

## 11. 文件选择、回收站与轻量撤回

### 11.1 操作边界

文件操作通过独立端口执行：

```text
FileActionService
└─ WindowsRecycleBinAdapter
   ├─ preflight(paths)
   ├─ move_to_recycle_bin(paths)
   ├─ can_restore(operation_id)
   └─ restore(operation_id)
```

不得在 UI 事件处理器中直接调用删除 API。

### 11.2 删除前预检

预检至少返回：

- 实际文件数量与总大小；
- 完整路径清单；
- 文件是否仍存在、是否自扫描后发生变化；
- 回收站是否可用；
- 本次操作能否支持撤回；
- 是否选中了某重复组的全部副本。

发生变化的文件不得沿用旧报告直接删除，必须要求重新确认或重扫。

### 11.3 Windows 实现策略

优先使用支持系统回收站语义的 Windows Shell 文件操作接口。具体采用 `IFileOperation`、Shell COM 或经过验证的封装库，需要在实现阶段通过中文路径、长路径、部分失败和恢复能力的真实测试决定。

不得用普通永久删除冒充“移入回收站”。当环境不支持回收站或无法撤回时，必须在执行前明确告知；第一阶段不提供绕过回收站的永久删除入口。

### 11.4 最近一次批量撤回

仅保存最近一次操作的轻量清单：

```text
LastFileAction
├─ operation_id
├─ original_paths[]
├─ completed_items[]
├─ failed_items[]
├─ created_at
└─ restore_capability
```

恢复时原路径已有同名文件则停止该项，不得覆盖。应用不建立用户可浏览的长期隔离区或隔离历史。

## 12. 缓存与持久化

SQLite 缓存属于性能优化，不是文件身份真相。

### 12.1 建议表

```text
global_settings
duplicate_configs
conflict_configs
runs
files
resources
findings
reports
checkup_records
last_file_action
```

`files`：

```text
path, size, mtime_ns, file_sha256, scan_status, error
```

`resources`：

```text
file_path, ordinal, type, group, instance,
offset, stored_size, memory_size, compression, payload_sha256
```

`payload_sha256` 允许为空，只在资源碰撞且需要比较时计算。

### 12.2 命中与失效

初期缓存命中可以使用 `normalized_path + size + mtime_ns`。这只是快速判断；提供“强制完整重扫”。文件删除、移动或发生变化后，相关报告条目标记为 stale，而不是静默伪造当前状态。

报告、缓存和应用状态默认放在 Mods 目录之外，避免下一次被扫描或被游戏加载。

## 13. 进度、取消与并发

每次运行通过统一任务接口报告：

```text
ProgressEvent
├─ phase
├─ current_item?
├─ completed_count
├─ total_count?
├─ bytes_processed?
└─ message_key
```

- 取消使用协作式取消标记，文件块读取、目录遍历和资源解析之间检查；
- 不在线程执行中直接更新 UI；
- 同一配置默认只允许一个活动运行；
- 两项功能是否允许同时大量扫描同一磁盘，在性能验证前默认串行；
- 取消后保存 `cancelled` 状态和已经确认的错误，不把部分报告标成完整。

## 14. 技术栈决策与建议项目结构

### 14.1 GitHub 调研后的技术栈门

GitHub 调研没有找到完整匹配本 PRD 的成熟成品，但找到了可直接减少 DBPF 实现成本的候选组件。

正式初始化仓库前先完成一个受限 spike：

1. 使用 .NET 8 与 MIT 许可的 `LlamaLogic.Packages` 只读打开受控和真实 package；
2. 输出完整 ResourceKey、尺寸与压缩元数据，并与 s4pe 对拍；
3. 测试大目录遍历、取消、内存占用和 Windows 回收站行为；
4. 记录第三方依赖版本、许可证和升级策略。

如果 spike 通过，推荐采用 .NET 8 作为后端与桌面主进程，DBPF 通过本项目的只读 `PackageReaderPort` 适配 `LlamaLogic.Packages`。GUI 在 WPF、WinUI 3 与 Avalonia 中另做最小验证后决定。

如果 .NET 路线不通过，再比较 Electron／TypeScript + `@s4tk/models`，以及 Python + 经加固的 MIT `sims4-workspace` parser。不得为了保留既定语言而引入不必要的跨进程桥接。

### 14.2 逻辑项目结构

以下结构表达模块边界，不用文件扩展名提前锁死实现语言：

```text
sims4-mod-doctor/
├─ app/                            # 桌面入口
├─ cli/                            # 开发与回归验证入口
├─ core/                           # 模型、枚举、错误、能力声明
├─ application/                    # 两类 run service、组合协调与文件动作
├─ config/                         # 全局、重复、冲突三类配置
├─ scan/                           # 范围图、遍历、指纹、稳定性
├─ package/
│  ├─ PackageReaderPort            # 本项目只读接口
│  ├─ ThirdPartyPackageAdapter     # 候选：LlamaLogic.Packages
│  └─ PackageSafetyLimits
├─ analyze/                        # 重复、健康、覆盖、关系、脚本
├─ diagnostics/                    # Sims 4、MCCC 与关联器
├─ persistence/                    # SQLite、配置与报告
├─ report/                         # 两类报告与导出
├─ platform/windows/               # 路径、回收站、长路径
├─ ui/
│  ├─ home/
│  ├─ duplicates/
│  ├─ conflicts/
│  ├─ checkup/
│  └─ shared/
├─ tests/                          # 单元、性质、集成与平台测试
└─ third-party-notices/            # 依赖许可证与来源记录
```

桌面 GUI 框架仍属于实现选择；核心、应用层和报告模型不得依赖具体 GUI 框架。

## 15. 分期开发与验收门

以下是架构建议的交付顺序；每一期都必须独立运行和验证。具体版本号可在建立仓库后调整，但依赖顺序不应倒置。

### 阶段 A：重复检测核心

- 任意单目录、多目录与启用状态；
- 父子目录范围图与每文件只读一次；
- 大小分组、流式 SHA-256、稳定性检查；
- JSON 与静态 HTML 报告；
- Unicode、长路径、权限错误和确定性排序测试。

暂不包含 DBPF、缓存和删除。

### 阶段 B：可用的重复检测桌面流程

- 首页的重复文件入口；
- 目录选择、范围保存、进度和取消；
- 重点结果静默排序；
- 多选与一键勾选重复副本；
- Windows 回收站预检、删除、部分失败与最近一次轻量撤回。

### 阶段 C：DBPF 读取能力验证与封装

- 选定第三方库并固定版本、许可证与只读适配器；
- header、index、constant fields；
- 未压缩、zlib、RefPack/QFS 和混合样本；
- 空、损坏、截断与恶意 count 样本；
- 使用真实 package 与 s4pe 对拍每个 TGI、offset、stored size、memory size 和 compression；
- 只比较总数不构成验收通过。

### 阶段 D：多项内部冲突

- Mods 内局部范围选择；
- TGI 倒排；
- 碰撞资源按需解压与 payload hash；
- 资源相同、内容覆盖、内容未知、包含与部分重叠；
- 本次范围内附带重复文件；
- 独立 ConflictReport。

### 阶段 E：健康检查与最近报错诊断

- package 与脚本归档结构健康；
- 经过验证后逐步加入依赖、版本和引用检查；
- Sims 4 原生日志解析；
- MCCC 可选增强；
- 四级行动优先级、独立可信度和未完成分析统计。

### 阶段 F：组合体验与性能

- 可选一键体检协调器；
- 两份报告分标签展示及独立失败；
- SQLite 增量缓存；
- 结果筛选、搜索和历史入口；
- 经实验验证后再考虑加载顺序和预期覆盖规则。

## 16. 测试策略

### 16.1 自动测试

- 受控文件重复组、同大小不同内容、空文件；
- 多扫描源与父子目录范围图；
- Unicode、空格、特殊字符和长路径；
- reparse point 不跟随；
- 扫描中发生变化；
- DBPF constant fields 全组合；
- 损坏、截断、越界与不支持压缩；
- TGI 多重集合，不能用普通 set 丢失重复项；
- 报告排序与稳定选择；
- 日志解析器对未知格式保持降级；
- 回收站部分失败和恢复冲突。

### 16.2 本机真实验证

- 当前玩家真实 Mods 组织方式；
- EA app／Steam 实际路径待覆盖；
- Documents 默认位置与 OneDrive 重定向；
- 小型、中型和大型 Mods 集合；
- 真实合并包、默认替换、汉化、补丁和损坏文件；
- s4pe 对拍；
- 文件删除进入回收站以及最近一次撤回。

### 16.3 支持状态

功能与平台对外标记为：

```text
自动测试通过
本机真实测试通过
多用户验证通过
跨平台验证通过
```

代码能够运行不等于已经正式支持。

## 17. 安全与隐私

- 默认全部本地处理，不上传 Mods、错误日志或报告；
- 不自动联网识别作者、下载页或新版；
- 报告导出前提示其中可能包含本地用户名和完整路径；
- HTML 报告对所有文件名、路径和日志文本进行转义；
- ZIP／DBPF 解析设置大小、数量和解压上限，防止损坏或恶意文件消耗无限资源；
- 不执行 `.ts4script` 内代码，只读取归档结构和静态模块路径；
- 不根据日志、文件名或修改时间自动删除文件。

## 19. 开始编码前的准入条件

进入阶段 A 前应完成：

- PRD `0.15-review` 与本架构的入口、配置、结果和文件操作一致性检查；
- 完成 .NET 8 + `LlamaLogic.Packages` 技术 spike，并记录通过或否决证据；
- 建立项目仓库、确定运行时版本和测试命令；
- 收集不含隐私的受控重复文件夹样本；
- 明确报告和缓存目录位于 Mods 之外；
- 确认首轮只实现重复检测核心，不顺手混入 DBPF 或删除功能。

进入阶段 C 前应额外完成：

- 固定 s4pe 对拍流程；
- 建立真实 DBPF 回归语料及其来源记录；
- 为不支持的版本、压缩和损坏输入定义结构化错误；
- 设置资源数量、内存与解压安全上限。

进入任何删除功能前应额外完成：

- Windows 回收站真实验证；
- 中文、长路径、部分失败和恢复冲突测试；
- 删除前文件稳定性复核；
- 明确无法撤回时的用户提示。

## 20. 本版结论

v3 将产品体验与底层技术正式分开：

- 玩家看到两个独立任务和一个可选组合入口；
- 后端共享安全扫描、DBPF、日志、缓存和报告基础设施；
- 两项功能的配置、运行和报告仍彼此隔离；
- 重复判定只依据完整文件内容；
- 冲突分析保存资源事实，不把覆盖自动写成有害；
- 正常信息默认聚合，未完成分析明确暴露；
- 文件写操作只作用于用户明确选择，并使用 Windows 回收站；
- 每一阶段必须以自动测试和真实样本证据过门，不能用“代码能跑”替代验证。

这份架构可以作为后续项目初始化、任务拆分与实现评审的技术基线；若与 PRD 后续版本冲突，先更新 PRD 的产品结论，再同步修改本架构。
