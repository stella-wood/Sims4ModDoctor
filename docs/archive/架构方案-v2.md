# Sims 4 Mod Doctor 架构方案 v2

> 状态：讨论稿  
> 目标平台：Windows，本地离线运行  
> 总目标：做成一个集合式 Sims 4 Mod 诊断工具，同时解决重复文件与资源冲突问题。

---

## 1. 产品目标

用户选择一次 `Mods` 文件夹后，可以执行两种检查：

1. **快速体检**
   - 检测字节完全相同的重复文件。
   - 不解析 DBPF，速度快，结论确定。

2. **完整体检**
   - 包含快速体检的全部结果。
   - 解析 `.package` 内部资源索引。
   - 检测不同 package 是否提供相同 TGI 资源。
   - 在必要时比较资源内容，区分“重复内容”与“不同内容互相覆盖”。

最终输出一份统一报告，而不是两个互不相关的小程序。

---

## 2. 基本原则

### 2.1 默认只读

- 扫描、解析和生成报告时不修改 `Mods` 内任何文件。
- 不自动删除文件。
- 后续若增加清理功能，采用可恢复的“移至隔离区”，并保存恢复清单。

### 2.2 区分事实与推测

报告中的结论分为三类：

- **已确认**：例如两个文件 SHA-256 完全一致。
- **已确认存在覆盖**：两个 package 提供相同 TGI，但内容不同。
- **疑似关联**：例如资源集合高度相似，可能是新旧版本。

“存在相同 TGI”只说明资源重叠，不自动等于有害冲突。

### 2.3 小步实现，最终保持完整目标

开发时按 v0.1、v0.2、v0.3 分期验收，但最终产品仍是一个集合工具。每一期都必须能独立运行和验证，避免一次生成整套代码后难以定位错误。

## 3. 用户看到的功能

### 3.1 首页

- 选择或自动发现 Mods 文件夹。
- `快速体检` 按钮。
- `完整体检` 按钮。
- 显示扫描进度、当前文件和可取消按钮。
- 显示上次扫描时间与缓存状态。

### 3.2 报告分类

#### A. 完全重复文件

两个或多个文件字节完全一致，即使文件名和目录不同。

报告内容：

- 完整路径
- 文件大小
- 修改时间
- SHA-256
- 可释放空间
- “移至隔离区”候选项（后续版本）

这是唯一可以给出强清理建议的类别，但仍由用户选择保留哪一份。

#### B. 包含或合并关系

例如单独 Mod 的全部资源已经包含在某个合并包中。

报告内容：

- A 是否为 B 的资源子集
- 相同资源数量
- 相同内容数量
- 不同内容数量
- 是否可能为“单包＋合并包重复安装”

#### C. 资源覆盖

两个 package 含有相同 TGI。

继续细分为：

- **相同 TGI、相同内容**：冗余资源，可能来自合并包或重复打包。
- **相同 TGI、不同内容**：发生真实覆盖，但可能是正常补丁、汉化或默认替换。
- **相同 TGI、内容暂时无法比较**：已确认重叠，影响未知。

#### D. 疑似新旧版本

根据资源集合包含率、内容变化、文件名和目录关系给出候选，不自动清理。

文件名只作为辅助信号，不能单独决定两个 Mod 是否相同。

#### E. 无法读取

- 权限不足
- 文件扫描过程中发生变化
- DBPF header 损坏
- 索引越界或被截断
- 暂不支持的压缩方式

错误必须记录到报告，不因单个坏文件终止整个扫描。

## 4. 核心数据流程

```text
选择 Mods 目录
      │
      ▼
建立文件清单
      │
      ├── 快速体检 ──► 大小分组 ──► SHA-256 ──► 完全重复组
      │
      └── 完整体检 ──► 解析 DBPF 索引 ──► 建立 TGI 倒排表
                                           │
                                           ▼
                                  只读取发生重叠的资源内容
                                           │
                                           ▼
                                  内容 hash／关系分类
                                           │
                                           ▼
                                   统一 JSON＋HTML 报告
```

重要的性能策略：不为每个资源无条件解压。先通过 TGI 找到碰撞，只读取和比较有碰撞的资源内容。

## 5. 检测逻辑

### 5.1 完全重复文件

1. 按文件大小分组。
2. 大小唯一的文件不可能与其他文件完全相同，可跳过 SHA-256。
3. 只对同大小组进行流式 SHA-256。
4. 相同 SHA-256 归为一个重复组。

不根据文件名、修改时间或目录直接判断重复。

### 5.2 TGI 资源重叠

为每个非删除资源保存：

```text
package_path
type
group
instance
offset
stored_size
memory_size
compression
```

建立倒排表：

```text
(type, group, instance) -> [package A, package B, ...]
```

只有列表长度大于 1 的 TGI 才进入内容比较阶段。

### 5.3 资源内容比较

对发生重叠的资源：

1. 若存储内容字节已经完全一致，直接判定内容相同。
2. 否则按压缩方式解压。
3. 对解压后的 payload 计算 SHA-256。
4. payload hash 相同：内容相同。
5. payload hash 不同：内容不同，发生覆盖。
6. 无法解压：标记为“内容未知”，不猜测。

### 5.4 package 关系判断

禁止使用“相同 TGI 集合＝同一个 Mod”的绝对规则。

采用以下关系：

- **文件完全相同**：整个文件 SHA-256 相同。
- **资源等价**：TGI 多重集合相同，且每个资源的 payload hash 相同。
- **资源包含**：A 的资源全部存在于 B；再区分内容相同与被修改。
- **部分重叠**：仅报告交集数量、双方总数和包含率。
- **疑似版本关系**：资源包含率高且文件名等辅助信号相符。

相似度阈值必须通过真实 Mods 样本调试，不能先把 `0.9` 或 `0.5` 当成通用事实。

### 5.5 结论的两个维度

不要把所有结果压成单一“高／中／低风险”。报告分别显示：

- **确定性**：已确认／启发式推测／未知。
- **关系类型**：重复／冗余包含／内容覆盖／正常覆盖待确认。

这样不会把“确定存在覆盖”误写成“确定有害”。

## 6. DBPF 解析要求

### 6.1 已知基础

- Magic：`DBPF`
- Sims 4 常见文件版本：major `2`、minor `1`
- Header：96 字节
- 整数：小端序
- 资源键：Type `uint32`、Group `uint32`、Instance `uint64`

### 6.2 indexType 与 constant fields

资源索引开头的 `indexType` 使用下列 flags：

- `0x01`：Type 为公共常量
- `0x02`：Group 为公共常量
- `0x04`：Instance 高 32 位为公共常量

设为常量的字段只在索引头保存一次，不在每条记录中重复。解析器必须根据 flags 动态读取，禁止假定每条索引记录固定长度。

### 6.3 防御性校验

在任何 seek 或分配之前校验：

- 文件长度至少为 header 长度
- magic 和支持的版本
- `index_position + index_size` 不越过文件末尾
- `index_count` 合理，不可据损坏值进行巨大内存分配
- 每条记录读取前剩余字节足够
- `offset + stored_size` 不越界
- 32/64 位整数运算不溢出

解析失败只影响当前文件，并在报告中保留明确错误原因。

### 6.4 v0.2 验证方式

先做解析器验证，再接入冲突分析。

测试语料至少包括：

- 无 constant field
- 分别启用 Type、Group、InstanceHi constant
- 多项 constant 的组合
- 空 package
- 未压缩资源
- zlib 资源
- RefPack/QFS 资源
- 混合压缩 package
- 损坏与被截断的 package

使用真实 package 与 s4pe 对拍：

- 非删除资源数量一致
- 每个 TGI 三元组一致
- 保留重复项，按列表或多重集合比较
- 抽样核对 offset、stored size、memory size 和 compression

只比较总数不足以证明解析正确。

## 7. 加载顺序策略

初期不宣称能够确定“最终哪个 package 获胜”。

报告默认只显示：

> package A 与 package B 提供相同 TGI，内容相同或不同。

加载顺序功能必须通过控制实验验证：

1. 制作两个 TGI 相同但游戏内结果明显不同的测试包。
2. 交换文件名，记录结果。
3. 交换目录层级，记录结果。
4. 修改 `Resource.cfg` Priority/PackedFile 配置，记录结果。
5. 固定并记录游戏版本。

验证完成后再增加“预计生效文件”，且界面注明推断依据。

---

## 8. `.ts4script` 的处理

`.ts4script` 与 DBPF package 分开分析。

第一阶段只可将它作为普通文件参与 SHA-256 重复检测；后续单独增加：

- ZIP 结构校验
- Python 模块路径清单
- 同名模块碰撞
- 整个脚本包重复
- 疑似新旧脚本版本

不得把 `.ts4script` 冲突混入 TGI 模型。

## 10. 缓存设计

完整扫描后使用 SQLite 缓存：

### files

```text
path
size
mtime_ns
file_sha256
scan_status
error
```

### resources

```text
file_path
ordinal
type
group
instance
offset
stored_size
memory_size
compression
payload_sha256
```

`payload_sha256` 可为空，仅在资源发生重叠、需要比较时计算。

缓存命中条件可先采用 `path + size + mtime_ns`。它属于性能优化，不是绝对身份判断；提供“强制完整重扫”选项。

---

## 11. 文件系统安全与稳定性

- 默认不跟随目录 junction、符号链接或其他 reparse point，避免循环和重复扫描。
- 扫描前后比较文件大小与修改时间；若发生变化，标记后稍后重试一次。
- 支持 Unicode 文件名和长路径。
- 单个文件无法读取时继续扫描。
- 报告和隔离区默认放在 Mods 目录外，避免下一次被重新扫描。
- 不根据修改时间自动决定“保留新版”。

## 12. 分期开发计划

### v0.1：可靠的重复文件体检

范围：

- 选择目录
- 递归发现 `.package`，扩展名大小写不敏感
- 不跟随 reparse point
- 按大小分组
- 流式 SHA-256
- 终端摘要
- JSON 报告
- 简单静态 HTML 报告
- 错误收集

明确不包含：

- DBPF
- TGI
- SQLite 缓存
- 自动删除或移动
- 新旧版本猜测

验收标准：

- 相同内容、不同文件名：正确归组
- 相同大小、不同内容：不误报
- 空文件：可处理
- Unicode 和长路径：可处理
- 无权限文件：报告错误但不中断
- 文件扫描时变化：不输出错误 hash
- 输出顺序确定，多次运行报告稳定

### v0.2：DBPF 解析器验证版

- 只实现 header 和 index
- 支持 constant fields
- 保存完整索引元数据
- 不做冲突结论
- 与 s4pe 对拍真实 package
- 建立固定回归语料

### v0.3：资源重叠体检

- 建立 TGI 倒排表
- 输出 package 之间的资源重叠
- 按需读取碰撞资源
- 区分相同内容与不同内容
- 输出包含／合并关系
- 保持默认只读

### v0.4：缓存与可恢复清理

- SQLite 增量缓存
- 扫描进度与取消
- 隔离区
- 恢复清单
- 报告筛选和搜索

### v0.5：高级诊断

- `.ts4script` 模块碰撞
- 经验证的加载顺序推断
- 疑似新旧版本候选
- 用户可维护的“预期覆盖／忽略规则”
- 更完整的桌面界面

## 13. v0.1 的推荐技术选择

- Python 3.12+
- 第一版尽量只使用标准库：`pathlib`、`hashlib`、`json`、`html`、`argparse`
- hash 采用分块读取，不把大文件一次载入内存
- 逻辑层与报告层分离，之后可以无痛接 GUI
- 测试使用 `pytest`；若坚持零依赖，也可先用 `unittest`

第一版优先做 CLI＋HTML 报告。桌面 GUI 等核心扫描和 DBPF 解析稳定后再接，避免同时调试界面与底层格式。

---

## 14. 当前不做的事情

- 不自动从网络识别 Mod 作者或下载新版。
- 不根据文件名直接删除旧版本。
- 不承诺发现所有游戏崩溃原因。
- 不把所有相同 TGI 都称为有害冲突。
- 不修改、合并或重写用户 package。
- 不扫描 Tray，除非以后作为独立功能增加。

---

## 15. 最终验收目标

一个合格的 Sims 4 Mod Doctor 应当做到：

1. 用户只选择一次 Mods 文件夹。
2. 快速体检能可靠找出完全重复文件。
3. 完整体检能找出 package 资源重叠。
4. 能区分“相同 TGI 且内容相同”与“相同 TGI 但内容不同”。
5. 能识别常见的单包与合并包包含关系。
6. 不把推测伪装成确定事实。
7. 默认不改变任何 Mod 文件。
8. 任意单个坏文件不会使整个扫描失败。
9. DBPF 解析结果经过真实 package 与 s4pe 对拍验证。
10. 所有清理操作可恢复，并且必须由用户明确选择。
